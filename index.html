Quick start

Thirty minutes to wire Ticket Flow into a team. Prefer the Flow view once you know the steps.

1. Copy skill and rules

Copy .cursor/skills/ticket-flow/ and .cursor/rules/*.mdc into your product repo’s .cursor/ directory (or open this repo as a multi-root workspace).

  • Skill — the checklist the agent follows.
  • ticket-flow.mdc — routes trigger phrases to the skill.
  • ticket-handoff.mdc — Impact Area + tests on handoff/PR.

Next: wire the thin script wrappers to your CLIs.

2. Configure scripts

Edit wrappers under scripts/ so they call your tools. Unconfigured scripts exit with an error — they never invent ticket text or claim a chat send succeeded.

  • issue-get.sh → Jira / Linear / gh issue view
  • git-branch.sh, git-commit.sh, git-push.sh, git-pr.sh
  • notify-chat.sh → webhook or chat CLI (channel required)

Next: initialize a private progress board.

3. Progress board

Copy docs/progress-template.md to .local/progress.md (gitignored). Use it for morning multi-ticket queues.

Next: try a phrase that loads the skill.

4. Run a ticket

In Cursor chat, say something like:

work on ticket PROJ-123

or fix bug PROJ-123 / process morning queue. Expect Confirm gates before commit and before PR.

Vague requirements first? Use the playbook review-markdown before tickets exist, then return here for Develop one story.

Where are you starting?

Choose what you already have. Start there, then work through one step at a time.

Ticket Flow sequences how an IDE agent moves from a real ticket ID to a PR—with human Confirm gates—without becoming a platform.

    Script wrappers and failures
    
    
      
    Wrappers forward to existing CLIs. They must not reimplement tracker or chat business logic.
    
      
      
        
    • Unconfigured issue-get.sh / notify-chat.sh exit non-zero with instructions.
      • 
        
    • git-branch.sh refuses a dirty tree and reuses an existing ticket branch if present.
      • 
        
    • git-push.sh blocks direct push to main/master.
      • 
        
    • git-pr.sh seeds an Impact Area body (or accepts a body file).
      • 
      
    
      
    On failure: report the error envelope, offer recovery, do not invent success.

    FAQ
    
    
    
      What is Ticket Flow?
      
    A thin orchestration layer—skill, rules, and scripts—that sequences ticket ID → merged change with human Confirm gates. Not a product platform.
    
    
    
    
    
      Does this site create PRs?
      
    No. It only displays guidance. PRs happen in your local clone via configured scripts and your code host.
    
    
    
    
    
      Why two Confirm gates?
      
    One before commit (diff + Impact Area) and one before push/PR (title + body). Silence never counts as Confirm.
